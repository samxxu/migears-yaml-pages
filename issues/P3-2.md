# P3-2 — The same semantic value is accepted differently from the XML side (see …

## Finding / 问题

- EN: The same semantic value is accepted differently from the XML side (see xml-pages for the full example): YAML requires native scalars, so `required: 1` and `rows: '4'` are errors where XML accepts the equivalent strings.
- 中文: 同一语义值与 XML 侧接受面不同（完整例子见 xml-pages 一节）：YAML 要求原生标量，required: 1 与 rows: '4' 报错，而 XML 接受等价的字符串。
- Where / 位置: `src/Compiler.php:53-63 vs migears-xml-pages/src/Compiler.php:561-578`
- Verification / 验证: reproduced / 已实证

- 2026-09-28 · `owner — migears-yaml-pages` · `deferred` — real, and deliberate on both sides, so no code
  changes here. YAML hands the shared compiler native scalars, so `required: 1` arrives as an integer where a
  boolean is due and `rows: '4'` as a string where a positive integer is due; `tests/CompilerTest.php:1104-1114`
  pins the refusal. XML reads its attributes as strings and coerces them —
  `migears-xml-pages/src/Compiler.php:576-592` (`toBool`) and `:604-612` (`toInt`). Each reading is right for
  its own syntax, and the divergence is written down as deliberate in `tests/FrontEndParityTest.php:35-45`
  ("making them agree would mean breaking one of the two"); the native-scalar rule itself is documented in
  both README halves (`README.md:126-127` EN, `README.md:524-525` CN) and `spec.md:102-103` (§4.2). Making the
  two agree is a behaviour change on one side — a user-owned decision this pass does not take — so the item
  stays visible instead of being closed.
